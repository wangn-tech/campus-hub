# CampusHub 核心链路压测方案

## 1. 目标与边界

本方案用于获取可复核的性能基线，并在发布前发现容量、缓存回源、Kafka 投递和 WebSocket 广播退化。压测只针对隔离的 staging 环境；禁止携带生产 Token、真实用户数据或对生产执行写入压力。

当前应用未提供 Prometheus 应用指标，第一阶段以压测器输出、Nginx/容器资源、MySQL 慢查询、Redis `INFO`、Kafka consumer lag 和 ES 节点统计为证据。待指标端点落地后，将同一场景接入 Grafana 看板。

## 2. 场景与数据

| 场景 | 链路 | 负载 | 通过条件 |
|---|---|---:|---|
| 活动列表 | Gin → MySQL/缓存 → 响应 | 20、50、100 并发，各 5 分钟 | 无 5xx；记录 RPS、P50/P95/P99、DB/Redis 资源 |
| 活动搜索 | Gin → ES，故障时 MySQL 回退 | 同上；分别执行 ES 正常/停止 | 无 5xx；响应头符合模式；记录两种模式延迟 |
| 报名与票据 | HTTP → MySQL 事务 → outbox → Kafka | 预置测试账号，每账号仅一次 | 无超卖；状态日志、票据与 outbox 一致；允许且验证重复请求 409 |
| 通知/认证状态 | 业务事务 → outbox → Kafka → WebSocket | 10/50 并发触发，双实例订阅 | 不丢事件；重复事件不生成重复通知；记录端到端延迟 |
| 群消息与离线补偿 | WebSocket → 持久化 → Kafka 广播 → HTTP 补偿 | 10/50/100 并发连接 | ACK/消息唯一；断线后 `/messages/offline` 可补齐 |

首次运行只产出基线，不填写虚假容量结论。建议在固定规格的 staging 机器上重复 3 次，记录中位结果；确认目标 SLO 后再将 P95、错误率和 consumer lag 阈值写入发布门禁。

## 3. 执行步骤

1. 使用 `backend/deploy/docker/docker-compose.yml` 启动隔离依赖，执行迁移并导入固定的分类、活动、组织者、报名用户与群聊种子数据；记录镜像版本、CPU/内存和数据量。
2. 启动一个实例，预热 60 秒后运行读场景；再启动两个 `instance_id` 不同的实例，执行 Kafka/WebSocket 场景。
3. 运行列表与搜索基线：

   ```sh
   cd backend
   CAMPUSHUB_LOAD_BASE_URL=http://127.0.0.1:8080 \
     go run ./scripts/loadtest -scenario activity-list -concurrency 50 -duration 5m
   CAMPUSHUB_LOAD_BASE_URL=http://127.0.0.1:8080 \
     go run ./scripts/loadtest -scenario activity-search -concurrency 50 -duration 5m
   ```

4. 停止 ES 后重复搜索场景，确认结果头为 `X-Search-Mode: mysql-fallback`；恢复 ES 后确认索引模式恢复。
5. 写链路必须使用专用测试 Token 和预先分配的一次性活动/账号。使用 `custom` 场景请求目标接口，禁止通过脚本自动注册或污染共享环境：

   ```sh
   CAMPUSHUB_LOAD_TOKEN="$LOAD_TEST_TOKEN" \
   CAMPUSHUB_LOAD_SCENARIO=custom CAMPUSHUB_LOAD_METHOD=POST \
   CAMPUSHUB_LOAD_PATH="/api/v1/activities/$LOAD_ACTIVITY_ID/registrations" \
   go run ./scripts/loadtest -concurrency 1 -duration 1s
   ```

6. 使用 `backend/scripts/wsprobe` 和 `backend/scripts/ci-integration.sh` 的双实例模式验证聊天、通知、认证和报名事件；同时采集 Kafka lag 与 outbox pending/failed 数量。

## 4. 脚本说明与结果归档

`backend/scripts/loadtest` 是零第三方依赖的 Go HTTP 压测器，输出 JSON：请求数、RPS、HTTP 状态分布、传输错误、P50/P95/P99 和 `passed`。默认仅接受 `2xx`；用 `-expected-status 409` 或 `CAMPUSHUB_LOAD_EXPECTED_STATUS=409` 验证幂等冲突。内置 `activity-list`、`activity-search` 两个无副作用场景；`custom` 仅供人工显式配置写链路。

每次运行在 `docs/test/results/YYYY-MM-DD-<environment>.md` 记录：Git SHA、前端/后端镜像、机器规格、数据规模、完整命令、JSON 输出、MySQL/Redis/Kafka/ES 观测、结论和异常。`results/` 只提交脱敏后的汇总，Token、请求中的个人信息和生产地址不得入库。

## 5. 故障与一致性检查

- Redis 不可用：读请求允许降级回源，但不能返回错误数据；记录数据库压力和恢复时间。
- Kafka 不可用：业务事务必须成功写入 outbox；恢复后 relay 重试并最终投递，通知幂等。
- ES 不可用：搜索回退 MySQL，检查 `X-Search-Mode` 和基础结果。
- 双实例 WebSocket：同一事件可到达正确用户所在实例；重复投递不应产生重复持久化记录，客户端以 HTTP 补偿为准。
- 报名并发：核对容量、`registration_status_logs`、tickets 与 outbox_events，确保无超卖和无孤儿票据。
