# 可观测性设计

## 1. 文档目的

本文定义 CampusHub 的日志、指标、健康检查、链路追踪、告警、优雅启停以及关键中间件监控方案。

## 2. 可观测性目标

- 请求可追踪；
- 故障可定位；
- 指标可量化；
- 异常可告警；
- 服务可平滑重启；
- Kafka、Redis、MySQL、Elasticsearch 的异常能及时发现。

## 3. 日志设计

### 3.1 日志库

使用 Zap 输出结构化日志。

- 开发环境可使用 console 格式；
- 测试和生产环境使用 JSON；
- 默认输出到 stdout；
- 日志级别支持 debug、info、warn、error。

### 3.2 日志字段

通用字段：

- `timestamp`，使用 Unix 毫秒时间戳；
- `level`；
- `caller`；
- `message`；
- `trace_id`；
- `service`；
- `env`；
- `instance_id`。

请求日志增加：

- `method`；
- `path`；
- `status_code`；
- `latency_ms`；
- `client_ip`；
- `user_agent`；
- `user_id`，如已认证。

### 3.3 日志规范

- 错误日志必须包含上下文和 Trace ID；
- 不记录密码、Token、完整学号、密钥；
- 不使用无上下文的 `print`；
- 请求日志和业务日志通过 Trace ID 关联；
- 第三方调用应记录耗时、结果和请求 ID。

## 4. 请求 ID / Trace ID

- 入口中间件为每个请求生成或透传 Trace ID；
- 响应头和响应体中可返回 Trace ID；
- 日志、Kafka Header、WebSocket 消息中传递 Trace ID；
- 异步消费者继续使用原事件 Trace ID。

## 5. 指标设计

### 5.1 HTTP 指标

需要采集：

- 请求总数；
- 请求耗时；
- 状态码分布；
- 并发请求数；
- 请求体大小；
- 响应体大小；
- 404、429、5xx 数量。

标签：

- method；
- path template；
- status；
- env。

### 5.2 Go Runtime 指标

- goroutine 数量；
- GC 耗时；
- 内存分配；
- heap 使用；
- CPU；
- 文件描述符。

### 5.3 MySQL 指标

- 连接池使用；
- 空闲连接；
- 等待连接次数；
- 慢查询；
- 事务耗时；
- 错误数量。

### 5.4 Redis 指标

- 连接池状态；
- 命令耗时；
- 命中率；
- Key 淘汰；
- 慢查询；
- 错误数量。

### 5.5 Kafka 指标

- 生产成功/失败数量；
- 消费成功/失败数量；
- 消费者组 Lag；
- 消费耗时；
- 重试次数；
- DLQ 数量；
- 分区分配变化。

### 5.6 Elasticsearch 指标

- 查询耗时；
- 写入耗时；
- 查询错误率；
- 索引文档数量；
- 集群健康；
- 搜索消费者 Lag；
- 全量重建进度。

### 5.7 WebSocket 指标

- 当前连接数；
- 在线用户数；
- 新增连接数；
- 异常关闭数；
- 心跳超时数；
- 消息发送成功率；
- 消息延迟；
- 单用户连接数。

## 6. 健康检查

### 6.1 Liveness

```text
GET /health
```

只表示进程存活，不检查全部依赖，避免容器被频繁误杀。

### 6.2 Readiness

```text
GET /ready
```

检查：

- MySQL；
- Redis；
- Kafka；
- Elasticsearch；
- 对象存储，如启用。

未就绪时负载均衡不应继续转发流量。

服务进程可在依赖暂时不可达时启动并保持存活；此时 `/health` 正常、`/ready` 返回未就绪。依赖恢复后无需重启进程即可重新接入流量。Readiness 响应仅暴露各依赖的 `up/down` 状态，具体连接错误只写入结构化日志。

## 7. 链路追踪

一期可预留 OpenTelemetry：

- HTTP 入口创建 Span；
- Service、Repository、Redis、Kafka、ES 调用透传 Context；
- Kafka Header 传递 Trace ID；
- WebSocket 消息携带 Trace ID。

如果资源有限，一期可先通过结构化日志和 Trace ID 满足排障，后续再接入完整链路追踪后端。

## 8. 告警建议

| 告警 | 建议条件 |
|---|---|
| HTTP 5xx 异常 | 短时间内 5xx 比例升高 |
| 接口延迟 | P95/P99 超阈值 |
| MySQL 连接池耗尽 | 等待连接持续增加 |
| Redis 不可用 | Ping 失败或命中率异常下降 |
| Kafka Lag | 消费者组积压持续增加 |
| DLQ 积压 | 死信消息数量大于 0 并持续增长 |
| ES 集群异常 | 集群状态非 green/yellow 或查询错误升高 |
| WebSocket 异常关闭 | 异常关闭率明显升高 |
| 磁盘空间 | 服务或中间件磁盘使用率超阈值 |

阈值应结合压测结果和环境容量确定。

## 9. 仪表盘规划

建议仪表盘分组：

1. 总览：QPS、错误率、延迟、实例数；
2. HTTP：路径、方法、状态码；
3. MySQL：连接池、慢查询、事务；
4. Redis：内存、命中率、命令耗时；
5. Kafka：Topic、Lag、生产消费；
6. Elasticsearch：集群、查询、写入；
7. WebSocket：连接数、在线用户、消息投递；
8. Runtime：goroutine、内存、GC。

## 10. 优雅启停

### 10.1 启动

- 加载并校验配置；
- 初始化 MySQL、Redis、Kafka、ES 客户端；
- 恢复必要状态；
- 启动 HTTP、WebSocket、Consumer、Cron；
- Readiness 通过后接入流量。

### 10.2 停止

1. 接收退出信号；
2. 停止接收新请求和新连接；
3. 通知 WebSocket 客户端；
4. 等待处理中的请求完成；
5. 提交 Offset 或保存消费进度；
6. 停止定时任务；
7. 关闭数据库和缓存连接；
8. 退出进程。

## 11. 事件与异步任务观测

每个事件应记录：

- Event ID；
- Event Type；
- Aggregate ID；
- Producer；
- Consumer Group；
- 重试次数；
- 处理耗时；
- 成功或失败；
- Trace ID。

异步任务必须能通过 Event ID 追踪完整生命周期。

## 12. 日志保留与采样

- 生产日志按团队策略集中采集和保留；
- 高频健康检查和调试日志可采样；
- 错误日志和安全审计日志不应随意丢弃；
- Kafka DLQ 和审计数据保留周期应符合业务要求。

## 13. 验证方式

上线前验证：

- 每个请求都有 Trace ID；
- `/health` 和 `/ready` 返回符合预期；
- Prometheus 指标可被采集；
- 核心依赖断开时 Ready 状态变化正确；
- Kafka 消费者异常时能看到 Lag 和错误日志；
- 服务停止时请求可平滑完成；
- WebSocket 断开和重连有指标记录。

## 14. 设计约束

1. 业务关键路径必须有日志和指标。
2. 日志不得包含敏感明文。
3. 指标标签应避免高基数字段，例如用户 ID、完整路径参数。
4. 健康检查不能产生过重负载。
5. 告警必须能定位到具体服务、实例和依赖。
6. 观测能力不能阻塞核心业务请求。
