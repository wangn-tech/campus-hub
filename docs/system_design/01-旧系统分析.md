# 旧系统分析

## 1. 文档目的

本文用于梳理旧后端 `is-Xiaoen/CampusHub` 的技术架构、业务模块、数据模型和可复用规则，为新后端重构提供边界，避免遗漏功能或直接照搬不合理设计。

## 2. 旧系统基本情况

旧项目是一个校园活动管理平台，主要技术包括：

- go-zero API 服务；
- go-zero RPC 服务；
- 独立 WebSocket 服务；
- MySQL；
- Redis；
- Watermill + Redis Stream；
- DTM 分布式事务；
- 七牛云对象存储；
- 阿里云/腾讯云 OCR；
- Prometheus；
- Elasticsearch v7 客户端依赖。

旧项目在物理上拆分了用户、活动、聊天三类服务，并通过 gRPC、Redis Stream、DTM 等机制完成服务协作。

## 3. 旧系统模块

### 3.1 用户模块

主要能力：

- 邮箱注册、登录、退出；
- Access Token / Refresh Token；
- 用户资料维护；
- 头像上传；
- 兴趣标签维护；
- 学生认证；
- 学生认证 OCR；
- 信用分；
- 信用分变更记录；
- 图片资源管理；
- QQ 邮箱验证码；
- 账号注销。

核心表：

- `users`；
- `user_credits`；
- `credit_logs`；
- `student_verifications`；
- `interest_tags`；
- `user_interest_relations`；
- `sys_images`。

### 3.2 活动模块

主要能力：

- 活动草稿、发布、审核、取消；
- 活动分类；
- 活动标签；
- 活动列表；
- 活动详情；
- 活动搜索；
- 活动报名；
- 活动报名取消；
- 活动票据；
- 票据核销；
- 活动状态日志；
- 标签使用统计；
- 浏览量统计；
- 活动推荐。

核心表：

- `activity_tag_stats`；

### 3.3 聊天与通知模块

主要能力：

## 4. 旧架构中的关键协作

### 4.1 活动创建

旧流程大致为：

1. 用户提交活动；
2. 活动服务创建活动记录；
3. 同步活动标签；
4. 通过 DTM 协调标签使用次数等跨服务操作；
5. 活动进入待审核或发布状态。

### 4.2 活动报名

旧流程大致为：

1. 校验活动时间、状态、报名窗口；
2. 校验学生认证、信用分等报名条件；
3. 校验名额；
4. 创建报名记录；
5. 创建活动票据；
6. 更新活动当前报名人数。

### 4.3 活动群聊

旧系统在活动发布后创建活动群：

- 一个活动对应一个群；
- 活动组织者默认为群主；
- 报名成功用户加入群；
- 取消报名后应退出群；
- WebSocket 负责实时消息和通知投递。

### 4.4 学生认证

旧流程包含：

1. 用户提交认证资料和学生证图片；
2. OCR 识别学校、姓名、学号等信息；
3. 用户确认 OCR 结果；
4. 必要时进入人工审核；
5. 认证通过、拒绝、取消或超时；
6. 认证进度通过 WebSocket 推送。

## 5. 旧系统存在的问题

### 5.1 服务拆分成本较高

当前业务规模下，API、RPC、独立 WebSocket 服务数量较多，带来以下成本：

- 本地启动依赖复杂；
- 服务间调用链长；
- 调试和排错成本高；
- 部署和配置分散；
- 很多业务并不需要强拆为分布式服务。

### 5.2 数据模型重复

标签相关模型存在重复：

- 用户服务中有 `interest_tags`；
- 活动服务中有 `tag_cache`；
- 活动标签和兴趣标签语义相近但编号、同步逻辑分散；
- 标签同步失败会造成活动服务数据不完整。

新系统应统一标签模型，或明确标签类型和数据归属。

### 5.3 时间字段不统一

旧表中同时存在：

- Unix 秒级时间戳；
- MySQL `DATETIME`；
- Go `time.Time`；
- 毫秒或秒级混用风险。

新系统建议数据库统一使用 `DATETIME(3)`，业务层使用 `time.Time`，对外可按需要返回 Unix 时间戳。

### 5.4 API 路径不统一

前端当前同时调用：

- `/api/v1/activity/lists`；
- `/api/notifications`；
- `/api/users/{user_id}/groups`；
- `/api/groups/{group_id}`；
- `/api/messages/offline`。

部分接口还存在单复数和路径不一致问题，例如：

- `/api/v1/activity/list`；
- `/api/v1/activity/lists`；
- `/api/v1/activity/tags`；
- `/api/v1/interests/tags`。

新系统应统一收敛到 `/api/v1`。

### 5.5 DTM 使用复杂

旧系统引入 DTM 处理跨服务事务，但新系统采用模块化单体后，大部分操作可以在一个 MySQL 事务内完成，不需要继续引入 DTM。

跨系统一致性优先使用：

- 本地事务；
- Outbox 事件表；
- Kafka；
- 幂等消费；
- 补偿任务。

### 5.6 Elasticsearch 版本偏旧

旧项目使用 Elasticsearch v7 Go 客户端。新系统引入 Elasticsearch 9，并使用 `go-elasticsearch/v9`。

## 6. 可复用的业务规则

以下业务规则应在新系统中保留并明确：

- 活动必须有报名时间窗口和活动时间窗口；
- 活动报名开始时间不应晚于报名结束时间；
- 活动开始时间不应晚于活动结束时间；
- 报名截止后不能报名；
- 活动取消后不能继续报名；
- 同一用户对同一活动只能有一条有效报名记录；
- 报名成功后生成唯一票据；
- 一张票据只能核销一次；
- 活动可要求学生认证、信用分门槛或人工审批；
- 一个活动最多对应一个活动群；
- 活动组织者默认拥有活动管理权限；
- 学生认证资料属于敏感信息，需要加密和访问控制；
- 通知需要支持已读、全部已读和未读数量。

## 7. 新系统重构原则

1. 新系统采用 Go + Gin + GORM 的模块化单体。
2. MySQL 是唯一事实来源。
3. Redis 承担缓存、Token、验证码、分布式锁和在线状态。
4. Kafka 承担异步事件和最终一致性。
5. Elasticsearch 只承担活动搜索和聚合读模型。
6. WebSocket 只负责实时连接和消息投递，不保存唯一业务状态。
7. 不继续引入 DTM，优先使用本地事务 + Outbox。
8. 所有外部依赖通过 Docker Compose 统一启动。
9. 新接口统一使用 `/api/v1`，旧接口在迁移期可做兼容映射。
