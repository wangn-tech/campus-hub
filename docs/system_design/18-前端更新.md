# 前端更新

## 1. 文档目的

本文说明新后端完成后，现有前端为了与 Go + Gin + GORM + MySQL + Redis + Kafka + Elasticsearch 架构对齐，需要进行的接口、字段、状态、页面逻辑和实时通信改造。

本文只描述前端更新要求，不包含后端业务代码实现。

## 2. 更新范围

前端需要重点更新：

1. HTTP Base URL 和环境配置；
2. 登录、注册、刷新 Token、注销等认证接口；
3. 当前用户接口 `/users/me`；
4. 分类、标签和兴趣接口；
5. 活动列表、详情、发布和搜索接口；
6. 报名、审批、票据和核销流程；
7. 通知、群聊、消息接口；
8. 文件上传流程；
9. WebSocket 地址、认证和事件命名；
10. 页面状态展示和错误处理。

## 3. 全局配置更新

### 3.1 环境变量

前端不应继续写死旧服务器 IP，应按环境配置后端地址：

| 配置项 | 说明 |
|---|---|
| API Base URL | HTTP API 根地址 |
| WebSocket URL | WebSocket 根地址 |
| 上传地址 | 文件上传接口，通常由 API Base URL 拼接 |
| 环境标识 | development、staging、production |
| API 版本前缀 | 统一为 `/api/v1` |

生产环境建议通过同源反向代理访问，例如前端页面和 API 都由同一个网关域名提供，减少跨域和环境切换问题。

### 3.2 统一响应结构

前端 HTTP 封装需要与新后端统一响应结构对齐。建议响应包含：

| 字段 | 说明 |
|---|---|
| `code` | 业务码，成功为 0 |
| `message` | 提示信息 |
| `data` | 业务数据 |
| `trace_id` | 链路追踪 ID，便于排查问题 |

分页响应建议统一为：

| 字段 | 说明 |
|---|---|
| `list` | 当前页数据 |
| `total` | 总记录数 |
| `page` | 当前页码 |
| `page_size` | 每页数量 |

前端应避免在不同模块中分别解析 `records`、`items`、`list`、`data.list` 等多种分页字段。

## 4. 认证接口更新

### 4.1 接口路径

| 功能 | 旧路径 | 新路径 | Method |
|---|---|---|---|
| 登录 | `/api/v1/login` | `/api/v1/auth/login` | POST |
| 注册 | `/api/v1/register` | `/api/v1/auth/register` | POST |
| 退出登录 | `/api/v1/logout` | `/api/v1/auth/logout` | POST |
| 刷新 Token | `/api/v1/refresh_token` | `/api/v1/auth/refresh` | POST |
| 注销账号 | `/api/v1/logoff` | `/api/v1/auth/logoff` | POST |
| 重置密码 | `/api/v1/users/info/password/qq_email` | `/api/v1/auth/password/reset` | POST |

### 4.2 邮箱验证码

邮箱验证码接口统一为：

```text
/api/v1/email-codes
```

通过 `scene` 区分场景：

| 场景 | scene |
|---|---|
| 注册 | `register` |
| 忘记密码 | `forgot_password` |
| 注销账号 | `logoff` |

前端需要统一使用同一种 HTTP Method，不再在不同模块中混用 GET 和 POST。

### 4.3 Token 处理

前端需要：

- 登录后保存 `access_token` 和 `refresh_token`；
- 请求头统一携带 `Authorization: Bearer <access_token>`；
- Access Token 过期时调用刷新接口；
- Refresh Token 失效时清理本地登录状态并跳转登录页；
- 退出登录时清理用户信息、Token、WebSocket 连接和相关缓存；
- 不再通过接口参数传递当前用户 ID。

## 8. 报名与审批流程更新

### 8.1 报名接口

| 功能 | 新路径 | Method |
|---|---|---|
| 提交报名 | `/api/v1/activities/{id}/registrations` | POST |
| 查看活动报名记录 | `/api/v1/activities/{id}/registrations` | GET |
| 查看报名详情 | `/api/v1/registrations/{id}` | GET |
| 审批通过 | `/api/v1/registrations/{id}/approve` | POST |
| 审批拒绝 | `/api/v1/registrations/{id}/reject` | POST |
| 取消报名 | `/api/v1/registrations/{id}` | DELETE |

### 8.2 报名状态

| 状态 | 含义 | 前端展示 |
|---|---|---|
| `pending` | 待审批 | 已报名，等待组织者审核 |
| `approved` | 已通过 | 报名成功，可查看票据 |
| `rejected` | 已拒绝 | 报名未通过 |
| `cancelled` | 已取消 | 已取消报名 |
| `failed` | 报名失败 | 名额不足或条件不满足 |
| `expired` | 待审批超时 | 审核超时，可重新报名 |

### 8.3 页面逻辑调整

活动详情页需要区分两类活动。

无需审批活动：

1. 用户点击报名；
2. 后端返回 `approved`；
3. 响应中包含票据和活动群信息；
4. 页面展示报名成功、票据和进入群聊入口。

需要审批活动：

1. 用户点击报名；
2. 后端返回 `pending`；
3. 页面展示等待审核，不展示票据；
4. 组织者审批通过后，前端通过通知或刷新报名详情获取票据；
5. 审批拒绝或超时后，页面展示对应原因，并允许按规则重新报名。

前端不能在 `pending` 状态下提前展示票据码、核销码或活动群入口。

### 8.4 组织者审批页面

组织者需要新增或完善报名管理能力：

- 查看待审批人数；
- 查看报名用户基础信息；
- 查看学生认证状态或信用状态，如活动规则需要；
- 审批通过；
- 审批拒绝并填写原因；
- 取消用户报名；
- 查看报名状态变更记录。

审批操作需要防重复提交，并处理报名已取消、名额已变化、活动已结束等异常。

## 9. 票据与核销更新

### 9.1 票据接口

| 功能 | 旧路径 | 新路径 | Method |
|---|---|---|---|
| 票据列表 | `/api/v1/activity/tickets` | `/api/v1/tickets` | GET |
| 票据详情 | `/api/v1/activity/tickets/detail` | `/api/v1/tickets/{id}` | GET |

### 9.2 票据状态

| 状态 | 展示含义 |
|---|---|
| `unused` | 未使用 |
| `used` | 已核销 |
| `expired` | 已过期 |
| `void` | 已作废 |

### 9.3 票据展示规则

- 票据只在报名 `approved` 后存在；
- `pending` 报名不展示票据；
- 报名取消、活动取消后，票据应展示为作废；
- 活动结束或超过可核销时间后，票据展示为过期；
- 已核销票据需要展示核销时间和核销结果。

### 9.4 核销接口

| 功能 | 旧路径 | 新路径 | Method |
|---|---|---|---|
| 核销票据 | `/api/v1/activity/verify` | `/api/v1/check-ins` | POST |
| 核销记录 | 旧接口不完整 | `/api/v1/check-ins` | GET |

核销请求应包含：

- 票据码或票据 UUID；
- 活动 ID，如后端要求；
- 经度和纬度，可选；
- 客户端幂等 ID。

核销页面需要处理：

- 票据不存在；
- 票据不属于当前活动；
- 票据已核销；
- 票据已过期或作废；
- 不在核销时间；
- 无核销权限；
- 网络重复提交。

## 11. 文件上传更新

### 11.1 上传接口

| 功能 | 旧路径 | 新路径 | Method |
|---|---|---|---|
| 图片上传 | `/api/v1/images/upload` | `/api/v1/files/images` | POST |

### 11.2 上传流程

新流程统一为：

1. 前端选择文件；
2. 校验文件类型、大小和尺寸；
3. 调用上传接口；
4. 获取文件 ID、URL 和文件状态；
5. 业务表单保存文件 ID；
6. 提交业务数据。

适用场景包括：

- 头像；
- 活动封面；
- 学生证图片；
- 聊天图片；
- 其他后续扩展图片。

前端不应把 base64 图片或本地临时路径提交给业务接口。

## 12. 搜索更新

### 12.1 搜索入口

活动搜索统一使用：

```text
GET /api/v1/activities/search
```

该接口由 Elasticsearch 提供检索能力，支持：

- 关键词；
- 分类；
- 标签；
- 活动状态；
- 时间范围；
- 地点；
- 经纬度；
- 分页和排序。

### 12.2 搜索结果字段

搜索结果与活动列表字段尽量保持一致，避免页面维护两套数据结构。人数字段使用：

- `approved_participant_count`；
- `pending_participant_count`。

### 12.3 降级处理

如果 Elasticsearch 暂时不可用，后端可能降级到 MySQL 查询。前端需要接受降级场景下：

- 搜索能力变弱；
- 排序和聚合结果较少；
- 响应时间可能变长。

前端不需要为降级场景切换页面，但应正确展示后端返回的提示信息。

## 13. WebSocket 更新

### 13.1 连接地址

WebSocket 路径统一为：

```text
/ws
```

完整地址应根据当前环境自动推导，不继续写死局域网 IP。

### 13.2 连接流程

1. 前端建立 WebSocket 连接；
2. 连接建立后发送认证事件；
3. 后端校验 Token；
4. 认证成功后订阅当前用户相关通知和群消息；
5. 认证失败时关闭连接并引导重新登录；
6. 前端按固定间隔发送心跳；
7. 断线后使用指数退避重连；
8. 重连后重新认证并补齐离线消息。

### 13.3 统一事件命名

新系统统一使用小写下划线事件名。

客户端发送：

| 事件 | 说明 |
|---|---|
| `auth` | 认证 |
| `ping` | 心跳 |
| `send_message` | 发送消息 |
| `mark_read` | 标记已读 |

服务端发送：

| 事件 | 说明 |
|---|---|
| `auth_success` | 认证成功 |
| `auth_failed` | 认证失败 |
| `pong` | 心跳响应 |
| `ack` | 消息确认 |
| `new_message` | 新消息 |
| `notification` | 新通知 |
| `verify_progress` | 学生认证进度 |
| `registration_status_changed` | 报名状态变化 |
| `error` | 错误事件 |

前端需要移除或兼容旧的 `newMessage`、`verifyProgress`、`studentAuthUpdate` 等小驼峰监听名称。最终代码中应只保留一套事件常量。

### 13.4 消息 ACK

发送消息时前端应使用客户端消息 ID：

- 发送中：本地临时展示；
- 收到 ACK：替换为正式消息 ID；
- 发送失败：允许重试或提示失败；
- 重连后通过 HTTP 拉取历史消息，避免重复插入。

## 16. 错误处理更新

前端需要根据错误码和状态进行统一处理：

| 场景 | 处理方式 |
|---|---|
| 未登录 | 跳转登录页 |
| Token 过期 | 尝试刷新 Token |
| Token 无效 | 清理登录状态并重新登录 |
| 无权限 | 提示无权限并返回安全页面 |
| 资源不存在 | 展示不存在或已删除 |
| 报名重复 | 刷新当前报名状态 |
| 名额已满 | 提示名额已满并刷新活动 |
| 票据已核销 | 展示票据当前状态 |
| ES 不可用 | 接受后端降级结果 |
| 网络超时 | 支持重试或稍后再试 |

所有错误提示优先使用后端返回的 `message`，同时保留前端兜底文案。

## 17. 上线切换策略

建议按以下顺序切换：

1. 后端提供新接口；
2. 前端先在开发环境切换 Base URL；
3. 更新 HTTP 封装和认证流程；
4. 按模块替换活动、报名、票据、通知、聊天接口；
5. 接入 WebSocket 新事件；
6. 与后端进行联调和异常场景验证；
7. 预发环境完整回归；
8. 生产环境通过网关切换到新后端；
9. 观察接口错误、通知、消息和搜索质量；
10. 确认稳定后删除旧接口兼容层。

如果后端迁移期提供旧路径兼容，前端也应尽快切换到新路径，兼容层只作为临时方案。

## 19. 结论

前端更新的核心不是简单替换 URL，而是围绕新后端的领域模型进行对齐：

- 当前用户由 Token 识别；
- 标签统一建模；
- 报名和审批状态分离；
- 票据在审批通过后生成；
- 群成员只包含有效报名用户；
- 搜索由 Elasticsearch 提供并支持降级；
- 文件上传与业务提交解耦；
- WebSocket 事件命名、ACK 和重连规则统一。

完成本文改造后，前端才能与新后端的接口契约、数据一致性和实时通信模型保持一致。
