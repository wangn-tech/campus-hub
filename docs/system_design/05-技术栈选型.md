# 技术栈选型

## 1. 文档目的

本文明确新 CampusHub 后端采用的语言、框架、中间件、客户端库和辅助工具，并说明选型理由、职责边界和替代方案。

## 2. 基础技术栈

| 类别 | 技术 | 版本建议 | 职责 |
|---|---|---|---|
| 语言 | Go | 1.24+ | 后端业务开发 |
| Web 框架 | Gin | v1.x | HTTP 路由、中间件、请求处理 |
| ORM | GORM | v1.25+ | 数据访问、事务、关联查询 |
| 关系型数据库 | MySQL | 8.x | 业务主存储 |
| 缓存 | Redis | 7.x | 缓存、Token、验证码、锁、在线状态 |
| 消息队列 | Kafka | 3.x+，KRaft 模式 | 异步事件和系统解耦 |
| 搜索引擎 | Elasticsearch | 9.x | 活动搜索和聚合 |
| 容器 | Docker / Docker Compose | 最新稳定版 | 环境一致性和本地依赖编排 |

## 4. Kafka 客户端选择

### 4.1 推荐：segmentio/kafka-go

推荐理由：

- API 比传统 Sarama 更简洁；
- 对 Go context 支持较好；
- 支持 Reader、Writer、消费者组和手动提交；
- 适合模块化单体中的事件生产和消费。

适用场景：

- Outbox Relay 发布事件；
- 搜索索引消费者；
- 通知消费者；
- 统计消费者。

### 4.2 备选：IBM/sarama

特点：

- 功能完整；
- 生态成熟；
- 配置项较多；
- API 和错误处理相对复杂。

如果团队已有 Sarama 经验，也可以使用 Sarama，但不建议在项目中混用两个 Kafka 客户端。

## 5. 本地缓存选择

### 5.1 推荐：Ristretto v2

推荐理由：

- 面向高并发场景；
- 支持内存成本控制；
- 支持 TTL；
- v2 支持泛型；
- 适合缓存低频变更的字典和配置数据。

适合缓存：

- 分类；
- 标签；
- 系统配置；
- 短 TTL 热门活动列表；
- 权限策略的静态部分。

不适合缓存：

- 报名名额；
- 票据状态；
- 核销结果；
- 账号注销、密码修改等强一致状态。

### 5.2 备选方案

| 库 | 特点 | 适用情况 |
|---|---|---|
| `go-cache` | 简单、直观、TTL 易理解 | 小规模项目或更重视可读性 |
| `FreeCache` | 内存管理严格 | 大容量、避免 GC 压力的场景 |
| `BigCache` | 适合大量条目 | 缓存对象多、生命周期短的场景 |

新系统推荐通过项目内部缓存接口封装 Ristretto，避免业务代码直接依赖第三方库。

## 6. Elasticsearch 客户端

使用：

```text
github.com/elastic/go-elasticsearch/v9
```

约束：

- Go 版本使用 1.24+；
- Elasticsearch 使用 9.x；
- 客户端封装在 `internal/search`；
- 业务 Service 不直接拼接底层 ES JSON 请求；
- 搜索索引同步通过 Kafka 完成。

## 7. WebSocket 选型

使用 `gorilla/websocket`。

职责：

- 连接升级；
- 文本/二进制消息读写；
- 心跳；
- 连接关闭；
- 客户端事件解析。

WebSocket Hub 由项目自行实现，用于管理：

- 连接集合；
- 用户与连接映射；
- 群组订阅；
- 消息广播；
- 多实例消息转发。

## 8. 配置管理选型

使用 Viper。

需要支持：

- 默认值；
- YAML 配置文件；
- 环境变量覆盖；
- 多环境配置；
- 配置结构校验；
- 敏感配置通过环境变量注入。

环境变量统一前缀：

```text
CAMPUSHUB_
```

## 9. 对象存储规划

### 9.1 本地开发

推荐使用 MinIO：

- S3 兼容；
- Docker Compose 可直接启动；
- 适合头像、活动封面、学生证图片等文件。

### 9.2 生产环境

可选择：

- MinIO 自建；
- 阿里云 OSS；
- 腾讯云 COS；
- 其他 S3 兼容存储。

后端通过 Storage 接口屏蔽具体实现。

## 10. 可观测性组件

| 能力 | 技术 | 说明 |
|---|---|---|
| 日志 | Zap | JSON 结构化日志 |
| 指标 | Prometheus Client | HTTP、MySQL、Redis、Kafka、ES 指标 |
| 指标展示 | Grafana，可选 | 仪表盘和告警 |
| 健康检查 | Gin 自定义接口 | `/health`、`/ready` |
| 链路追踪 | OpenTelemetry，可选 | 一期可预留，不强依赖 |
| Kafka 调试 | Kafka UI，可选 | 查看 Topic、消费者组和消息 |
| ES 调试 | Kibana，可选 | 查看索引、Mapping 和调试查询 |

## 11. 不建议继续引入的组件

| 组件 | 原因 |
|---|---|
| DTM | 新系统为模块化单体，大多数操作可在本地事务完成 |
| Watermill | 新系统统一使用 Kafka，不继续使用 Redis Stream 作为主消息机制 |
| 独立 RPC 框架 | 模块化单体内直接方法调用，减少部署和调试复杂度 |
| 多套缓存库 | 避免 Redis、本地缓存和消息流能力重复 |
| 直接 AutoMigrate 管理生产表结构 | 迁移不可审计，建议使用版本化迁移工具 |

## 12. 依赖使用原则

1. 第三方库必须有明确职责，不引入功能重复依赖。
2. 数据库、缓存、搜索、消息队列客户端应通过内部接口封装。
3. 业务代码优先依赖内部接口，而不是具体第三方实现。
4. 所有中间件必须能通过 Docker Compose 在本地启动。
5. 可选组件通过配置或 Compose Profile 控制，不强制所有环境启动。
6. 依赖版本应在开发开始前锁定，并在部署文档中记录。
